## 1. 这段代码负责什么

下单链路只做四件事：

```
① 判断能不能复用已有订单
② 查商品、算金额
③ 落库一笔订单（status = CREATE）
④ 向支付宝申请支付单，拿到支付表单链接（status = PAY_WAIT）
```

**边界很重要：**

| 属于下单              | 不属于下单         |
| ----------------- | ------------- |
| 校验商品、计算金额         | 用户是否真的付了钱     |
| 创建 `pay_order` 记录 | 更新支付成功状态      |
| 调支付宝生成支付表单        | 发货、开通会员、返利    |
| 返回 `pay_url` 给前端  | 超时关单（由定时任务负责） |

一句话：**下单 = 把「想买」变成「待支付」，并拿到一个可跳转的支付入口。**

## 4. 数据模型与表结构

### 4.1 表 `pay_order`

[`s-pay-mall.sql`](../docs/dev-ops/mysql/sql/s-pay-mall.sql)：

```sql
CREATE TABLE `pay_order` (
  `id`           int unsigned NOT NULL AUTO_INCREMENT COMMENT '自增ID',
  `user_id`      varchar(32) NOT NULL COMMENT '用户ID',
  `product_id`   varchar(16) NOT NULL COMMENT '商品ID',
  `product_name` varchar(64) NOT NULL COMMENT '商品名称',
  `order_id`     varchar(16) NOT NULL COMMENT '订单ID',
  `order_time`   datetime    NOT NULL COMMENT '下单时间',
  `total_amount` decimal(8,2) unsigned DEFAULT NULL COMMENT '订单金额',
  `status`       varchar(32) NOT NULL COMMENT '订单状态',
  `pay_url`      varchar(2014) DEFAULT NULL COMMENT '支付信息',
  `pay_time`     datetime    DEFAULT NULL COMMENT '支付时间',
  `create_time`  datetime    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`  datetime    NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uq_order_id` (`order_id`),
  KEY `idx_user_id_product_id` (`user_id`,`product_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

设计要点：

| 设计                             | 原因                                      |
| ------------------------------ | --------------------------------------- |
| `order_id` 唯一索引                | 订单号是业务主键，必须全局唯一；也是支付回调的 `out_trade_no`  |
| `(user_id, product_id)` 普通索引   | 下单前要按「谁买什么」查是否有未支付订单                    |
| `total_amount decimal(8,2)`    | 金额绝不能用 float/double；精度 2 位、最大 999999.99 |
| `pay_url varchar(2014)`        | 存支付宝返回的**整个 form HTML**（不是 URL）；长度需留意   |
| `id` 自增                        | 查询「最新一笔」时靠 `order by id desc`           |
| `create_time/update_time` 自动维护 | 免去手写时间                                  |

### 4.2 实体映射

[`pay_order_mapper.xml`](../s-pay-mall-web/src/main/resources/mybatis/mapper/pay_order_mapper.xml#L5-L18) 的 `resultMap` 负责下划线 ↔ 驼峰：

```
user_id → userId      product_id → productId      order_id → orderId
order_time → orderTime    total_amount → totalAmount    pay_url → payUrl
```

```xml
<insert id="insert">
    insert into pay_order(user_id, product_id, product_name, order_id, order_time,
                          total_amount, status, create_time, update_time)
    values(#{userId}, #{productId}, #{productName}, #{orderId}, #{orderTime},
           #{totalAmount}, #{status}, now(), now())
</insert>

<!-- 查最近一笔：注意 limit 1 + order by id desc -->
<select id="queryUnPayOrder">
    select product_id, product_name, order_id, order_time, total_amount, status, pay_url
    from pay_order
    where user_id = #{userId} and product_id = #{productId}
    order by id desc
    limit 1
</select>

<!-- 支付单创建成功后回写链接 -->
<update id="updateOrderPayInfo">
    update pay_order set pay_url = #{payUrl}, status = #{status}, update_time = now()
    where order_id = #{orderId}
</update>

<!-- 超时关单候选：PAY_WAIT 且下单超过 30 分钟 -->
<select id="queryTimeoutCloseOrderList">
    SELECT order_id as orderId FROM pay_order
    WHERE status = 'PAY_WAIT' AND NOW() >= order_time + INTERVAL 30 MINUTE
    ORDER BY id ASC LIMIT 50
</select>
```

```java
            .orderId(unpaidOrder.getOrderId())

            unpaidOrder.getProductName(), unpaidOrder.getOrderId(),

            .payUrl(payOrder.getPayUrl()).build();
}
```

**③ 新建订单**

```java
ProductVO productVO = productRPC.queryProductByProductId(shopCartReq.getProductId());
String orderId = RandomStringUtils.randomNumeric(16);   // 16 位纯数字

orderDao.insert(PayOrder.builder()
        .userId(...).productId(...).productName(productVO.getProductName())
        .orderId(orderId)
        .totalAmount(productVO.getPrice())     // 金额以服务端查询结果为准

        .status(CREATE.getCode())
        .build());
```

### 第 6 步｜生成支付单

```java
private PayOrder doPrepayOrder(String productId, String productName,
                               String orderId, BigDecimal totalAmount) throws AlipayApiException {
    AlipayTradePagePayRequest request = new AlipayTradePagePayRequest();
    request.setNotifyUrl(notifyUrl);
    request.setReturnUrl(returnUrl);

    JSONObject bizContent = new JSONObject();
    bizContent.put("out_trade_no", orderId);        // 回传的商户订单号
    bizContent.put("total_amount", totalAmount.toString());
    bizContent.put("subject", productName);
    bizContent.put("product_code", "FAST_INSTANT_TRADE_PAY");
    request.setBizContent(bizContent.toString());

    String form = alipayClient.pageExecute(request).getBody();   // 自动提交表单 HTML

    PayOrder payOrder = new PayOrder();
    payOrder.setOrderId(orderId);
    payOrder.setPayUrl(form);
    payOrder.setStatus(PAY_WAIT.getCode());
    orderDao.updateOrderPayInfo(payOrder);
    return payOrder;
}
```

`pageExecute` 返回的是**一整段 HTML 表单**，不是 URL。前端把它写入页面，浏览器会自动 POST 到支付宝收银台。

**验证路径：**

1. 调接口 → 返回 HTML；

## 6. 订单状态机

[`Constants.OrderStatusEnum`](../s-pay-mall-common/src/main/java/cn/bugstack/common/constants/Constants.java#L33-L45)：

| 状态            | 含义           | 由谁写入                   |
| ------------- | ------------ | ---------------------- |
| `CREATE`      | 订单已落库，支付单未创建 | 下单（insert）             |
| `PAY_WAIT`    | 支付单已创建，等待付款  | 下单（updateOrderPayInfo） |
| `PAY_SUCCESS` | 支付成功         | 支付回调 / 补偿任务            |
| `DEAL_DONE`   | 交易完成（发货完成）   | 业务侧（当前未实现）             |
| `CLOSE`       | 超时关单         | 定时任务                   |

```
                    ┌──────────┐
                    │  CREATE  │  订单已创建
                    └────┬─────┘
          建支付单失败 →  │ 停留在 CREATE（可补单）
                         │ 建支付单成功
                    ┌────▼─────┐
                    │ PAY_WAIT │  等待支付
                    └──┬────┬──┘
         30 分钟未付 │    │ 收到支付成功
                    │    │
             ┌──────▼─┐ ┌▼───────────┐
             │ CLOSE  │ │ PAY_SUCCESS│
             └────────┘ └─────┬──────┘
                            │ 发货完成
                       ┌────▼─────┐
                       │DEAL_DONE │
                       └──────────┘
```

**状态流转铁律：**

- 只能**单向**前进，绝不回退；
- 每次更新都要能回答「原状态是什么」——这正是当前 SQL 缺失的部分（见第 9 节）。

## 7. 幂等：三种「已存在订单」的处理

用户重复点击「立即购买」是最常见的场景。代码用**同一个查询 + 三种分支**覆盖：

| 数据库最新订单状态                                   | 处理                          | 效果                |
| ------------------------------------------- | --------------------------- | ----------------- |
| `PAY_WAIT`                                  | 直接返回已有 `orderId` + `payUrl` | 不新建、不再调支付宝        |
| `CREATE`                                    | 用已有订单信息补建支付单                | `orderId` 不变，链接补齐 |
| 无记录 / `PAY_SUCCESS` / `CLOSE` / `DEAL_DONE` | 查询商品 → 新建订单                 | 允许再次购买            |

为什么 `CREATE` 要单独处理？

因为 `insert` 和 `doPrepayOrder` **不在同一事务**（`createOrder` 没有 `@Transactional`）。如果调支付宝超时或抛异常，库里就会留下一条 `CREATE` 的「半成品订单」。这个分支就是**兜底补单**，避免用户卡在「有订单但没有支付入口」。

为什么 `PAY_SUCCESS` 走「新建」？

因为已经付过款的订单不能被复用，否则用户再买一次会看到「已支付」的旧链接。

## 8. 八个技术点

**① 为什么金额用** **`BigDecimal`，且从服务端查？**
`float/double` 有二进制精度误差（0.1+0.2≠0.3）；金额必须 `BigDecimal` + `decimal(8,2)`。金额若取自请求参数，用户可改价，所以必须服务端查商品定价。

**② 为什么订单号是 16 位随机数字？**
`RandomStringUtils.randomNumeric(16)` 生成 16 位数字，配合 `uq_order_id` 唯一索引。注意：纯随机**没有业务含义**（不含日期、用户），排查时无法从订单号看出时间。生产常用雪花算法或「日期+序列」。

**③ 为什么** **`queryUnPayOrder`** **要** **`limit 1`** **+** **`order by id desc`？**
同一用户可能对同一商品下过多笔单，只关心**最近一笔**。不加 `limit` 会返回多行导致 `TooManyResultsException`。

**④ 为什么插入和更新支付信息要分两步？**
必须先拿到支付宝返回的表单才能写 `pay_url`，而表单依赖 `orderId` 先落库/生成。所以顺序天然是「先 insert 拿 orderId → 再 update 支付信息」。

**⑤ 为什么** **`pay_url`** **用** **`varchar(2014)`？**
支付宝 `pageExecute` 返回的是一段带自动提交脚本的 HTML，长度可能上千字符。字段过短会截断，导致前端拿到残缺表单。生产建议改 `TEXT`。

**⑥ 为什么** **`pageExecute`** **是同步调用？**
`AlipayClient` 的 `pageExecute/execute` 都是同步 HTTP。下单接口会阻塞在支付宝的往返上，需配置超时，必要时加熔断。

**⑦** **`@Mapper`** **为什么不用写实现类？**
`mybatis-spring-boot-starter` 启动时扫描 `@Mapper` 接口，用 JDK 动态代理绑定 `namespace` 相同的 XML，方法名即 `id`。

**⑧ 为什么要有两个定时任务？**

- `TimeoutCloseOrderJob`：防止订单永远挂在 `PAY_WAIT`（30 分钟关单）；
- `NoPayNotifyOrderJob`：防止支付宝回调丢失导致「用户付了钱但订单还是 `PAY_WAIT`」。
  两者一进一退，构成**最终一致性**兜底。

## 9. 现有实现的八个问题

| # | 问题                                | 位置                                           | 风险   | 说明                                                                         |
| - | --------------------------------- | -------------------------------------------- | ---- | -------------------------------------------------------------------------- |
| 1 | **无事务**                           | `createOrder`                                | 🟠 中 | `insert` 与 `updateOrderPayInfo` 不在一个事务，异常时留下 `CREATE` 半成品（靠补单分支兜底，但会累积脏数据） |
| 2 | **并发重复下单**                        | `queryUnPayOrder` 后插入                        | 🟠 中 | 两个请求同时查不到订单 → 各插一条。缺 `(user_id, product_id, status)` 唯一约束或分布式锁             |
| 3 | **状态更新无 CAS**                     | `changeOrderPaySuccess` / `changeOrderClose` | 🟠 中 | `update ... where order_id=?` 不判断原状态，重复回调会重复执行、重复发事件                       |

| 6 | **`ProductRPC`** **是 mock**       | `ProductRPC`                                 | 🟡 低 | 商品名固定「测试商品」、价格固定 1.68，仅用于演示                                                |
| 7 | **日志打印参数错误**                      | `AliPayController#L43`、`#L59`                | 🟡 低 | 两处把 `getUserId()` 打了两次，缺少 `getProductId()`                                 |
