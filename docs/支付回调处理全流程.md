## 1. 这段代码负责什么

```
① 接收支付宝的异步 POST 通知
② 验签（证明请求真的来自支付宝）
③ 把订单从 PAY_WAIT 改为 PAY_SUCCESS，并记录支付时间
④ 发出「支付成功」事件，驱动发货/充值/返利
⑤ 返回 success，告诉支付宝「我收到了，别重试」
```

**边界：**

| 属于回调 | 不属于回调 |
|---|---|
| 验签、改订单状态、记录 `pay_time` | 生成支付单（下单时已完成） |
| 触发支付成功业务事件 | 页面跳转展示（那是 `return_url`） |
| 返回 `success` 停止重试 | 关单（由超时任务负责） |

**最重要的原则：**

> `notify_url` 是**唯一可信**的支付结果来源。前端轮询、`return_url` 跳转都不能用来改订单。

## 2. 完整时序

```
支付宝服务器               AliPayController              OrderServiceImpl          MySQL          EventBus
     │                          │                              │                     │               │
     │ ① POST alipay_notify_url  │                              │                     │               │
     │  form-urlencoded 参数     │                              │                     │               │
     │─────────────────────────>│                              │                     │               │
     │                          │ ② trade_status == SUCCESS ?  │                     │               │
     │                          │ ③ 收集 params                │                     │               │
     │                          │ ④ RSA2 验签                  │                     │               │
     │                          │   失败 → return "false"      │                     │               │
     │                          │                              │                     │               │
     │                          │ ⑤ changeOrderPaySuccess      │                     │               │
     │                          │─────────────────────────────>│                     │               │
     │                          │                              │ ⑥ update 状态       │               │
     │                          │                              │────────────────────>│               │
     │                          │                              │ ⑦ eventBus.post     │               │
     │                          │                              │─────────────────────────────────────>│
     │                          │                              │                     │     ⑧ 发货/充值 │
     │                          │<─────────────────────────────│                     │               │
     │ ⑨ "success"              │                              │                     │               │
     │<─────────────────────────│                              │                     │               │
```

**注意时序中的关键点：**

- 验签发生在**任何业务动作之前**；
- 改单与发事件在同一个方法里，中间没有事务包裹（这是现有实现的问题之一）；
- 返回 `success` 是最后一步，也是**唯一能让支付宝停止重试**的信号。

## 4. 回调报文长什么样

支付宝以 `application/x-www-form-urlencoded` **POST** 到 `notify_url`，参数类似：

| 参数 | 示例 | 说明 |
|---|---|---|
| `notify_type` | `trade_status_sync` | 通知类型 |
| `notify_id` | `2024102200222...` | 通知 ID |
| `notify_time` | `2024-10-22 10:00:00` | 通知时间 |
| `app_id` | `9021000132689924` | 应用 ID |
| `out_trade_no` | `8256182736459182` | **商户订单号**（关键） |
| `trade_no` | `2024102222001...` | 支付宝交易号 |
| `trade_status` | `TRADE_SUCCESS` | **交易状态**（关键） |
| `total_amount` | `1.68` | 订单总金额 |
| `buyer_pay_amount` | `1.68` | 买家实付金额 |
| `receipt_amount` | `1.68` | 实收金额 |
| `subject` | `测试商品` | 订单标题 |
| `gmt_payment` | `2024-10-22 09:59:58` | 付款时间 |
| `buyer_id` | `2088...` | 买家支付宝用户 ID |
| `seller_id` | `2088...` | 卖家 ID |
| `sign` | `xxx` | RSA2 签名 |
| `sign_type` | `RSA2` | 签名算法 |
| `charset` | `utf-8` | 字符集 |

**`trade_status` 的取值：**

| 值 | 含义 | 是否该改单 |
|---|---|---|
| `WAIT_BUYER_PAY` | 交易创建，等待付款 | ❌ |
| `TRADE_SUCCESS` | **支付成功** | ✅ |
| `TRADE_FINISHED` | 交易完结（不可退款） | ✅ 视业务 |
| `TRADE_CLOSED` | 交易关闭 | ❌（可置 CLOSE） |

## 5. 从 0 到 1：七个步骤

### 第 1 步｜准备公网可访问的回调地址

`notify_url` 必须：

- `http://` 或 `https://` 开头；
- **公网可直连**（本地开发用 natapp/ngrok 穿透）；
- **不能带自定义参数**（`?a=1` 会被判非法）。

```yaml
alipay:
  notify_url: http://xfg-studio.natapp1.cc/api/v1/alipay/alipay_notify_url
```

并在下单时传给支付宝：`request.setNotifyUrl(notifyUrl)`。

### 第 2 步｜定义回调接口

```java
@RequestMapping(value = "alipay_notify_url", method = RequestMethod.POST)
public String payNotify(HttpServletRequest request) throws AlipayApiException {
    // ...
}
```

**为什么用 `HttpServletRequest` 而不是 `@RequestParam`？**
支付宝参数是动态的（几十个字段、随版本变化），用 `parameterMap` 整体收集最稳，避免漏字段导致验签失败。

### 第 3 步｜先收参数

```java
Map<String, String> params = new HashMap<>();
Map<String, String[]> requestParams = request.getParameterMap();
for (String name : requestParams.keySet()) {
    params.put(name, request.getParameter(name));
}
```

⚠️ **必须使用原始参数**：不能 trim、不能转码、不能改大小写。验签是对「原始字符串」做的，改一个字符就失败。

### 第 4 步｜验签（核心）

```java
String sign = params.get("sign");
String content = AlipaySignature.getSignCheckContentV1(params);
boolean checkSignature = AlipaySignature.rsa256CheckContent(
        content, sign, alipayPublicKey, "UTF-8");
if (!checkSignature) {
    return "false";
}
```

`getSignCheckContentV1` 做的是：**剔除 `sign` 与 `sign_type` → 按 key 字典序 → `key=value` 用 `&` 拼接**。`rsa256CheckContent` 用**支付宝公钥**验证。

详见第 6 节。

### 第 5 步｜改订单状态

```java
// 订单服务
public void changeOrderPaySuccess(String orderId) {
    PayOrder payOrderReq = new PayOrder();
    payOrderReq.setOrderId(orderId);
    payOrderReq.setStatus(PAY_SUCCESS.getCode());
    orderDao.changeOrderPaySuccess(payOrderReq);   // update status + pay_time
    eventBus.post(JSON.toJSONString(payOrderReq)); // 发事件
}
```

```xml
<update id="changeOrderPaySuccess">
    update pay_order
    set status = #{status}, pay_time = now(), update_time = now()
    where order_id = #{orderId}
</update>
```

### 第 6 步｜返回 `success`

```java
return "success";
```

**这是整个回调的最后一步，也是最容易被写错的一步**，详见第 7 节。

### 第 7 步｜验证回调链路

**本地模拟回调（不经过支付宝）：**

回调是 form 表单，可以直接构造请求。但**没有真实签名会验签失败**，因此有三种验证方式：

1. **沙箱真实支付**（推荐）：用沙箱买家账号付款，支付宝会真实回调你的穿透地址；
2. **临时跳过验签**做联调：把 `checkSignature` 改为 true 并打日志（**只能本地，绝不可上线**）；
3. **用官方验签工具**生成签名后再构造请求。

**验证清单：**

- 回调后查库：`status = PAY_SUCCESS`、`pay_time` 有值；
- 日志出现「支付回调，交易状态: TRADE_SUCCESS」；
- 订阅者日志出现「收到支付成功消息」；
- 响应体必须**正好**是 `success`（没有引号、没有换行）。

## 6. 验签：整个回调的安全基石

### 6.1 验签做什么

```
① 把回调里除 sign、sign_type 外的所有参数
② 按参数名 ASCII 字典序排序
③ 拼成 a=1&b=2&c=3 的形式
④ 用「支付宝公钥」对 sign 做 RSA2 验签
```

### 6.2 代码对应的两个方法

| 方法 | 作用 |
|---|---|
| `AlipaySignature.getSignCheckContentV1(params)` | 生成待验签内容（剔除 sign/sign_type + 排序 + 拼接） |
| `AlipaySignature.rsa256CheckContent(content, sign, publicKey, "UTF-8")` | RSA2 验签 |

### 6.3 为什么必须验签

回调接口是**公开可访问**的。如果不验签，任何人构造：

```
POST /api/v1/alipay/alipay_notify_url
out_trade_no=自己的订单号&trade_status=TRADE_SUCCESS
```

就能把订单改成「已支付」——**零成本白嫖**。验签的价值在于：只有持有**支付宝私钥**的一方能生成可通过公钥验证的签名，而私钥只在支付宝手里。

> 与微信验签的对比：微信用「共享密钥 Token + SHA-1」，支付宝用「非对称密钥 + RSA2」。前者靠双方共享秘密，后者靠公私钥分离。

### 6.4 三个高频坑

| 坑 | 现象 | 解决 |
|---|---|---|
| 配成「应用公钥」而非「支付宝公钥」 | 永远验签失败 | 到开放平台复制「支付宝公钥」 |
| 对参数做了 trim/URL 二次解码 | 验签失败 | 使用 `request.getParameter` 原值 |
| 只对部分参数验签 | 验签失败或漏校验 | 必须用完整 `parameterMap` |

## 7. 返回值与重试机制

### 7.1 支付宝只认 `success`

| 返回内容 | 支付宝行为 |
|---|---|
| `success`（纯字符串） | ✅ 视为成功，**停止重试** |
| `false` / 其他任意内容 | ❌ 视为失败，**按策略重试** |
| 空响应 | ❌ 重试 |
| HTTP 5xx | ❌ 重试 |

**必须注意：**

- 不能返回 `Response.success()` 这种 JSON；
- 不能返回 `"success"`（带引号）；
- 不能返回 `success\n`（带换行）；
- 方法上不能有 `@ResponseBody` 之外的包装（`@RestController` 已包含）。

### 7.2 重试策略

支付宝异步通知失败后会在约 **25 小时内重试 8 次**，间隔逐次拉长（约 4 分钟 → 10 分钟 → 1 小时 → 2 小时 → 6 小时 → 15 小时）。

**因此回调必须满足两个条件：**

1. **幂等**：同一笔通知可能到达多次；
2. **快速响应**：不要做耗时业务（发货、发短信），否则会超时被重试。

### 7.3 现有代码的返回值问题

```java
if (!request.getParameter("trade_status").equals("TRADE_SUCCESS")) {
    return "false";        // ← 问题
}
```

- 对 `WAIT_BUYER_PAY` 返回 `false`，支付宝会**持续重试**；
- 对已处理过的通知也返回 `false`，制造无谓重试；
- 正确做法：**已识别且无需处理的状态，也应返回 `success`**（表示「我收到了，别再发」）。

同时 `request.getParameter("trade_status")` 可能为 `null`，直接 `.equals()` 会 NPE。

## 8. 幂等：重复回调必须无副作用

### 8.1 为什么必然重复

- 支付宝重试机制；
- 网络超时但对方已收到；
- 补偿任务与真实回调**并发**到达。

### 8.2 当前实现的问题

```xml
<update id="changeOrderPaySuccess">
    update pay_order set status = #{status}, pay_time = now()
    where order_id = #{orderId}
</update>
```

没有判断原状态。于是：

```
第 1 次回调 → 状态 PAY_WAIT → PAY_SUCCESS，发事件（发货）
第 2 次回调 → 状态已是 PAY_SUCCESS → 再次置 PAY_SUCCESS，再次发事件（重复发货！）
```

### 8.3 正确做法：CAS 更新 + 判断影响行数

```xml
<update id="changeOrderPaySuccess">
    update pay_order
    set status = #{status}, pay_time = now(), update_time = now()
    where order_id = #{orderId} and status = 'PAY_WAIT'
</update>
```

```java
public void changeOrderPaySuccess(String orderId) {
    int rows = orderDao.changeOrderPaySuccess(orderId);   // 返回 int
    if (rows == 0) {
        log.info("订单已处理或状态不允许，跳过 orderId:{}", orderId);
        return;                       // ← 关键：不重复发事件
    }
    eventBus.post(JSON.toJSONString(orderId));
}
```

**幂等的本质：让「状态迁移」本身成为唯一判据，而不是靠加锁或去重表。**

## 9. 补偿机制：回调丢了怎么办

即使有重试，回调仍可能永久丢失（地址变更、服务长时间宕机、消息被中间件吞掉）。所以必须有**主动查询**兜底。

### 9.1 补偿任务（`NoPayNotifyOrderJob`）

```java
@Scheduled(cron = "0/3 * * * * ?")   // 每 3 秒
public void exec() {
    List<String> orderIds = orderService.queryNoPayNotifyOrder();  // 1 分钟前仍 PAY_WAIT
    for (String orderId : orderIds) {
        AlipayTradeQueryRequest request = new AlipayTradeQueryRequest();
        AlipayTradeQueryModel bizModel = new AlipayTradeQueryModel();
        bizModel.setOutTradeNo(orderId);
        request.setBizModel(bizModel);

        AlipayTradeQueryResponse response = alipayClient.execute(request);
        if ("10000".equals(response.getCode())) {
            orderService.changeOrderPaySuccess(orderId);
        }
    }
}
```

**候选条件**（[mapper](../s-pay-mall-web/src/main/resources/mybatis/mapper/pay_order_mapper.xml#L57-L62)）：

```sql
SELECT order_id FROM pay_order
WHERE status = 'PAY_WAIT' AND NOW() >= order_time + INTERVAL 1 MINUTE
ORDER BY id ASC LIMIT 10
```

### 9.2 ⚠️ 这里有一个严重 bug

`code == "10000"` 只表示**查询接口调用成功**，不代表**用户已付款**。

支付宝 `alipay.trade.query` 对一笔**尚未支付**的订单同样返回 `code=10000`，此时 `trade_status` 是 `WAIT_BUYER_PAY`。

也就是说，当前代码会在用户**根本没付款**的情况下，把订单置为 `PAY_SUCCESS`。

**正确判断：**

```java
if ("10000".equals(response.getCode())
        && ("TRADE_SUCCESS".equals(response.getTradeStatus())
            || "TRADE_FINISHED".equals(response.getTradeStatus()))) {
    // 还应校验金额
    orderService.changeOrderPaySuccess(orderId);
}
```

### 9.3 关单任务（`TimeoutCloseOrderJob`）

```java
@Scheduled(cron = "0 0/10 * * * ?")   // 每 10 分钟
List<String> orderIds = orderService.queryTimeoutCloseOrderList();  // 超 30 分钟 PAY_WAIT
for (String orderId : orderIds) orderService.changeOrderClose(orderId);
```

```xml
<update id="changeOrderClose">
    update pay_order set status = 'CLOSE', pay_time = now() ...
    where order_id = #{orderId}
</update>
```

**两个问题：**

1. `changeOrderClose` 也**不判断原状态**，可能把已经 `PAY_SUCCESS` 的订单改成 `CLOSE`（如果两条任务并发）；
2. **关单还顺手写了 `pay_time`**，语义错误——没付款的订单不应有支付时间。

**修正：**

```sql
update pay_order set status = 'CLOSE', update_time = now()
where order_id = #{orderId} and status = 'PAY_WAIT'
```

### 9.4 两条任务的时序关系

```
下单 ──1min──> 补偿任务开始扫描 ──30min──> 关单任务开始扫描
         ↑                              ↑
      防止回调丢失                   防止订单永远挂起
```

两者必须都用 CAS 更新，否则会出现「刚支付成功又被关单」的竞态。

## 10. 事件总线与后续业务

### 10.1 装配

[`GuavaConfig`](../s-pay-mall-web/src/main/java/cn/bugstack/config/GuavaConfig.java#L29-L34)：

```java
@Bean
public EventBus eventBusListener(OrderPaySuccessListener listener) {
    EventBus eventBus = new EventBus();
    eventBus.register(listener);
    return eventBus;
}
```

### 10.2 发布

```java
eventBus.post(JSON.toJSONString(payOrderReq));
```

### 10.3 订阅

```java
@Subscribe
public void handleEvent(String paySuccessMessage) {
    log.info("收到支付成功消息，可以做接下来的事情，如；发货、充值、开户员、返利 {}", paySuccessMessage);
}
```

### 10.4 三个注意点

| 特点 | 说明 |
|---|---|
| **同步执行** | Guava `EventBus` 默认**同步**：`post` 会阻塞直到所有订阅者执行完 |
| **异常传播** | 订阅者抛异常会传回 `post` 调用方，导致回调返回 500 → 支付宝重试 |
| **无持久化** | 进程重启期间的事件会丢失，生产应换 MQ（RocketMQ/Kafka） |

**改进方向：**

```java
// 异步事件总线：避免阻塞回调、避免异常影响主流程
@Bean
public AsyncEventBus asyncEventBus(OrderPaySuccessListener listener) {
    AsyncEventBus bus = new AsyncEventBus(Executors.newFixedThreadPool(4));
    bus.register(listener);
    return bus;
}
```

## 11. 现有实现的九个问题

| # | 问题 | 位置 | 风险 | 影响 |
|---|---|---|---|---|
| 1 | **补偿任务误判已支付** | `NoPayNotifyOrderJob#L45-L47` | 🔴 严重 | `code=10000` 只代表查询成功，未付款订单也会被置为 `PAY_SUCCESS` |
| 2 | **改单无 CAS（不幂等）** | `changeOrderPaySuccess` | 🔴 高 | 重复回调 → 重复发事件 → 重复发货/充值 |
| 3 | **关单无 CAS** | `changeOrderClose` | 🟠 中高 | 可能把已支付订单改成 `CLOSE` |
| 4 | **先判状态后验签** | `payNotify#L74` | 🟠 中 | 未验签就信任参数；`trade_status` 为 null 时 NPE |
| 5 | **非成功状态返回 `false`** | `payNotify#L74-L76` | 🟠 中 | 触发支付宝无意义重试 |
| 6 | **不校验金额** | `payNotify` | 🟠 中 | 未比对 `total_amount` 与订单金额，存在少付风险 |
| 7 | **不校验 `app_id` / `seller_id`** | `payNotify` | 🟠 中 | 多应用共用公钥时可能串单 |
| 8 | **关单写了 `pay_time`** | `changeOrderClose` | 🟡 低 | 语义错误，后续统计失真 |
| 9 | **EventBus 同步 + 异常传播** | `changeOrderPaySuccess` | 🟠 中 | 订阅者异常导致回调失败 → 重试；进程重启丢消息 |

另外：`gmt_payment`、`alipayTradeNo` 取了值但完全没用；`log.error` 里打印 `userId` 两次（复制粘贴错误）。

## 12. 生产级加固方案

### 12.1 回调处理骨架（推荐结构）

```java
@PostMapping(value = "alipay_notify_url", produces = "text/plain;charset=utf-8")
public String payNotify(HttpServletRequest request) {
    try {
        Map<String, String> params = new HashMap<>();
        request.getParameterMap().forEach((k, v) -> params.put(k, v[0]));

        // ① 先验签
        String sign = params.get("sign");
        String content = AlipaySignature.getSignCheckContentV1(params);
        if (!AlipaySignature.rsa256CheckContent(content, sign, alipayPublicKey, "UTF-8")) {
            log.warn("验签失败 out_trade_no:{}", params.get("out_trade_no"));
            return "success";            // 已收到，不再重试
        }

        // ② 校验应用与状态
        if (!appId.equals(params.get("app_id"))) return "success";
        String status = params.get("trade_status");
        if (!"TRADE_SUCCESS".equals(status) && !"TRADE_FINISHED".equals(status)) {
            return "success";
        }

        String orderId = params.get("out_trade_no");
        BigDecimal notifyAmount = new BigDecimal(params.get("total_amount"));

        // ③ 校验订单与金额（CAS 更新在服务层完成）
        orderService.changeOrderPaySuccess(orderId, notifyAmount);

        return "success";
    } catch (Exception e) {
        log.error("支付回调处理异常", e);
        return "fail";                   // 让支付宝重试
    }
}
```

### 12.2 服务层幂等 + 金额校验

```java
@Override
public void changeOrderPaySuccess(String orderId, BigDecimal notifyAmount) {
    PayOrder order = orderDao.queryByOrderId(orderId);
    if (order == null) {
        log.error("订单不存在 orderId:{}", orderId);
        return;
    }
    if (order.getTotalAmount().compareTo(notifyAmount) != 0) {
        log.error("金额不一致 orderId:{} 订单:{} 回调:{}",
                orderId, order.getTotalAmount(), notifyAmount);
        return;
    }
    int rows = orderDao.changeOrderPaySuccess(orderId);   // where status='PAY_WAIT'
    if (rows == 0) {
        log.info("订单已处理，跳过 orderId:{}", orderId);
        return;
    }
    eventBus.post(orderId);
}
```

### 12.4 加固清单

| 项 | 当前 | 目标 |
|---|---|---|
| 验签顺序 | 先判状态后验签 | **先验签**再做任何判断 |
| 幂等 | 无 | `update ... where status='PAY_WAIT'` + 判断影响行数 |
| 金额 | 不校验 | 回调金额与订单金额比对 |
| 补偿判断 | 只看 `code` | `code` + `trade_status` |
| 关单 | 无条件更新 | CAS 到 `PAY_WAIT`，且不写 `pay_time` |
| 事件 | 本地同步 EventBus | MQ / 异步 + 本地消息表 |
| 返回值 | 非成功返回 `false` | 已处理一律 `success`，仅异常返回 `fail` |
