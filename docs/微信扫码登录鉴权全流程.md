## 1. 先搞清楚：这套方案到底在做什么

很多人第一次看这套代码会误以为它是 OAuth2 网页授权。**不是。**

| 方案                              | 适用场景              | 本文的实现 |
| ------------------------------- | ----------------- | ----- |
| OAuth2 网页授权 (`snsapi_userinfo`) | 在微信内置浏览器打开网页      | ❌ 未使用 |
| **公众号扫码事件 + ticket 中转**         | PC 网站/桌面端「微信扫码登录」 | ✅ 本文  |

本项目实现的是**扫码登录**：用户用手机微信扫 PC 页面上的二维码，微信服务器把「扫码事件」推送到我们的后端，后端通过 `ticket` 把「浏览器会话」和「微信 openid」关联起来，前端轮询拿到 openid 即视为登录成功。

**三个关键角色：**

- **浏览器（前端）**：请求二维码 ticket → 展示二维码 → 轮询登录结果
- **我们的后端**：向外调微信 API 拿 ticket；向内接收微信事件回调
- **微信服务器**：生成二维码、在用户扫码后主动 POST 事件给我们

**两个方向的通信，这是理解全流程的钥匙：**

```
后端 ──(主动调用 REST API)──> 微信 api.weixin.qq.com     ← 需要 access_token
后端 <──(被动接收事件推送)──── 微信服务器                ← 需要验签 + XML 解析
```

## 2. 核心原理与时序

```
浏览器            后端(LoginController)        微信 API          微信服务器        手机微信
  │                       │                       │                  │                │
  │ ① GET 取 ticket        │                       │                  │                │
  │──────────────────────>│                       │                  │                │
  │                       │ ② getToken(先查缓存)   │                  │                │
  │                       │──────────────────────>│                  │                │
  │                       │ ③ createQrCode        │                  │                │
  │                       │──────────────────────>│                  │                │
  │                       │<───── ticket ─────────│                  │                │
  │<──── ticket ──────────│                       │                  │                │
  │                       │                       │                  │                │
  │ ④ 前端展示二维码                                                     │                │
  │   https://mp.weixin.qq.com/cgi-bin/showqrcode?ticket=xxx            │                │
  │                                                                     │                │
  │                                       ⑤ 用户扫码 ──────────────────────────────────>│
  │                       │                       │  ⑥ POST receive   │                │
  │                       │<─────────────────────── 事件(SCAN+Ticket) ─│                │
  │                       │ ⑦ openidToken.put(ticket, openid)          │                │
  │                       │ ⑧ sendMessage 模板消息 ──────────────────>│                │
  │                       │                       │                  │                │
  │ ⑨ 轮询 check_login    │                       │                  │                │
  │──────────────────────>│                       │                  │                │
  │<─── openid（登录成功）─│                       │                  │                │
```

一句话概括：

> **前端拿 ticket 展示二维码 → 微信扫码后把 ticket 和 openid 一并发给后端 → 后端缓存映射 → 前端凭 ticket 换 openid。**

`ticket` 是贯穿全流程的**关联键**，理解了它就理解了整条线。

## 3. 关键概念扫盲

初学者最容易混淆的是两个 "token"，它们是**完全不同**的东西：

| 名称                | 配置项                   | 用途               | 谁生成                     | 有效期          |
| ----------------- | --------------------- | ---------------- | ----------------------- | ------------ |
| **服务器配置 Token**   | `weixin.config.token` | **验签**：证明请求来自微信  | 你自己在公众号后台随便填            | 永久（除非你改）     |
| **access\_token** | 无（运行时获取）              | **调用**微信 API 的凭证 | 微信 `cgi-bin/token` 接口返回 | 7200 秒（2 小时） |

其他概念：

| 概念            | 说明                                       |
| ------------- | ---------------------------------------- |
| `appid`       | 公众号唯一标识，公开                               |
| `appsecret`   | 公众号密钥，**必须保密**，泄露等于公众号被接管                |
| `originalid`  | 公众号原始 ID（如 `gh_e067c267e056`），用于回包时标识发送方 |
| `ticket`      | 二维码票据，由 `createQrCode` 生成，前端用它拼出二维码图片地址  |
| `openid`      | 用户在**该公众号**下的唯一标识（同一用户在不同公众号下 openid 不同） |
| `template_id` | 模板消息模板 ID                                |
| `scene_id`    | 二维码携带的场景值，用于区分不同业务来源                     |

## 5. 从 0 到 1：九个步骤

### 第 0 步｜微信侧准备（不写代码，但缺一不可）

1. 注册**微信公众号**（订阅号/服务号），拿到 `appid`、`appsecret`。
2. 公众号后台 → 设置与开发 → **基本配置**：记录 `appid`、`appsecret`，并把服务器公网 IP 加入 **IP 白名单**（否则调 `cgi-bin/token` 会报 `40164`）。
3. 设置与开发 → **服务器配置**：
   - `URL`：填 `http://<你的公网地址>/api/v1/weixin/portal/receive`
   - `Token`：自定义一个字符串（本项目 dev 环境是 `b8b6`）
   - `EncodingAESKey`：明文模式可不填
   - 消息加解密方式：**明文模式**
   - ⚠️ 点击「提交」的瞬间，微信会**立刻发一个 GET 请求**到你填的 URL 做验签——此时后端必须已启动且能通。
4. 本地开发需要**内网穿透**（natapp / ngrok / frp），把 `127.0.0.1:8080` 暴露成公网地址。
5. 在「模板消息」里选一个模板，拿到 `template_id`。

> 顺序很重要：**先启动服务，再点提交**。反了会一直提示「配置失败」。

### 第 3 步｜定义 DTO（数据结构先行）

写 HTTP 客户端前，先把报文结构定下来。这是「契约优先」的开发方式。

**① access\_token 响应** — [`WeixinTokenRes`](../s-pay-mall-domain/src/main/java/cn/bugstack/domain/res/WeixinTokenRes.java)

```java
@Data
public class WeixinTokenRes {
    private String access_token;   // 凭证
    private int expires_in;        // 有效期（秒），通常 7200
    private String errcode;        // 出错时才有
    private String errmsg;
}
```

**② 二维码请求** — [`WeixinQrCodeReq`](../s-pay-mall-domain/src/main/java/cn/bugstack/domain/req/WeixinQrCodeReq.java)

微信要求的三层嵌套结构：

```json
{
  "expire_seconds": 2592000,
  "action_name": "QR_SCENE",
  "action_info": { "scene": { "scene_id": 100601 } }
}
```

对应 Java 用 `@Builder` 嵌套静态类实现：

```java
public class WeixinQrCodeReq {
    private int expire_seconds;
    private String action_name;
    private ActionInfo action_info;

    public static class ActionInfo { Scene scene; }
    public static class Scene { int scene_id; String scene_str; }
}
```

`action_name` 的四种取值（见内部枚举 `ActionNameTypeVO`）：

| 值                    | 含义       | 有效期     |
| -------------------- | -------- | ------- |
| `QR_SCENE`           | 临时·整型参数  | 最长 30 天 |
| `QR_STR_SCENE`       | 临时·字符串参数 | 最长 30 天 |
| `QR_LIMIT_SCENE`     | 永久·整型参数  | 永久      |
| `QR_LIMIT_STR_SCENE` | 永久·字符串参数 | 永久      |

本项目用 `QR_SCENE` + `expire_seconds = 2592000`（30 天）。

**③ 二维码响应** — [`WeixinQrCodeRes`](../s-pay-mall-domain/src/main/java/cn/bugstack/domain/res/WeixinQrCodeRes.java)

```java
public class WeixinQrCodeRes {
    private String ticket;          // 核心字段
    private Long expire_seconds;
    private String url;             // 微信返回的可直接访问的二维码图片地址
}
```

**④ 模板消息** — [`WeixinTemplateMessageVO`](../s-pay-mall-domain/src/main/java/cn/bugstack/domain/vo/WeixinTemplateMessageVO.java)

```java
public class WeixinTemplateMessageVO {

    private String template_id;
    private String url;             // 点击消息跳转地址
```

### 第 4 步｜声明 API 契约（Retrofit 接口）

[`IWeixinApiService`](../s-pay-mall-service/src/main/java/cn/bugstack/service/weixin/IWeixinApiService.java) —— **只有注解，没有实现**：

```java
public interface IWeixinApiService {

    @GET("cgi-bin/token")
    Call<WeixinTokenRes> getToken(@Query("grant_type") String grantType,
                                  @Query("appid") String appId,
                                  @Query("secret") String appSecret);

    @POST("cgi-bin/qrcode/create")
    Call<WeixinQrCodeRes> createQrCode(@Query("access_token") String accessToken,
                                       @Body WeixinQrCodeReq req);

    @POST("cgi-bin/message/template/send")
    Call<Void> sendMessage(@Query("access_token") String accessToken,
                           @Body WeixinTemplateMessageVO vo);
}
```

注解语义：

| 注解                      | 作用             | 生成效果                                          |
| ----------------------- | -------------- | --------------------------------------------- |
| `@GET("cgi-bin/token")` | HTTP 方法 + 相对路径 | `GET https://api.weixin.qq.com/cgi-bin/token` |
| `@POST(...)`            | 同上             | `POST ...`                                    |
| `@Query("appid")`       | URL 查询参数       | `?appid=wx...`                                |
| `@Body`                 | 请求体            | 用 Jackson 序列化成 JSON                           |
| `Call<T>`               | 惰性请求对象         | 调 `.execute()` 才真正发送                          |

> 注意：`@Query` 和 `@Body` 的分工与微信 API 文档一一对应——`access_token` 永远在 **URL** 上，业务参数在 **body** 里。

### 第 5 步｜装配 Bean

**(A) Retrofit 装配** — [`Retrofit2Config`](../s-pay-mall-web/src/main/java/cn/bugstack/config/Retrofit2Config.java)

```java
@Configuration
public class Retrofit2Config {

    private static final String BASE_URL = "https://api.weixin.qq.com/";

    @Bean
    public Retrofit retrofit() {
        return new Retrofit.Builder()
                .baseUrl(BASE_URL)
                .addConverterFactory(JacksonConverterFactory.create())
                .build();
    }

    @Bean
    public IWeixinApiService weixinApiService(Retrofit retrofit) {
        return retrofit.create(IWeixinApiService.class);
    }
}
```

要点：

1. `baseUrl` **必须以** **`/`** **结尾**，否则拼接相对路径时会丢分隔符。
2. `JacksonConverterFactory` 负责 JSON ↔ DTO 双向转换。
3. `retrofit.create()` 是 **JDK 动态代理**：运行时生成接口实现，把注解翻译成 HTTP 请求。代理无状态，可安全复用。
4. `@Configuration` 类被 CGLIB 增强，即使把 `retrofit()` 写成普通方法调用，拿到的也是同一个单例。

**(B) 缓存装配** — [`GuavaConfig`](../s-pay-mall-web/src/main/java/cn/bugstack/config/GuavaConfig.java)

```java
@Bean(name = "weixinAccessToken")
public Cache<String, String> weixinAccessToken() {
    return CacheBuilder.newBuilder().expireAfterWrite(2, TimeUnit.HOURS).build();
}

@Bean(name = "openidToken")
public Cache<String, String> openidToken() {
    return CacheBuilder.newBuilder().expireAfterWrite(1, TimeUnit.HOURS).build();
}
```

| 缓存                  | Key      | Value         | 过期 | 目的                        |
| ------------------- | -------- | ------------- | -- | ------------------------- |
| `weixinAccessToken` | `appid`  | access\_token | 2h | 避免重复调 `getToken`（有每日次数限制） |
| `openidToken`       | `ticket` | `openid`      | 1h | 暂存「谁扫了哪个码」                |

> `@Resource` 默认**按字段名**匹配 Bean 名，所以 `WeixinLoginServiceImpl` 里的字段名必须写成 `weixinAccessToken` / `openidToken`，否则两个同类型 Bean 会注入冲突。

### 第 6 步｜验签与微信事件接入

这是整条链路里**最需要理解原理**的部分。

#### 6.1 验签算法 — [`SignatureUtil`](../s-pay-mall-common/src/main/java/cn/bugstack/common/weixin/SignatureUtil.java)

```java
public static boolean check(String token, String signature, String timestamp, String nonce) {
    String[] arr = new String[]{token, timestamp, nonce};
    sort(arr);                       // ① 字典序排序
    StringBuilder content = new StringBuilder();
    for (String s : arr) content.append(s);   // ② 拼接

    MessageDigest md = MessageDigest.getInstance("SHA-1");
    byte[] digest = md.digest(content.toString().getBytes());  // ③ SHA-1
    String tmpStr = byteToStr(digest);                         // ④ 转大写十六进制

    return tmpStr != null && tmpStr.equals(signature.toUpperCase());  // ⑤ 比对
}
```

四步记住：

```
排序(token, timestamp, nonce) → 拼接 → SHA-1 → 转十六进制大写 → 与 signature 比对
```

**为什么这样能证明请求来自微信？**

因为 `token` 是**只有你和微信知道的共享密钥**。攻击者即使拿到一次完整的请求参数，也只能「原样重放」，无法为一组**新的** timestamp/nonce 生成正确签名。安全性完全等价于 `token` 的保密性。

**实现细节坑点：**

- `byteToHexStr` 用 `>>> 4 & 0x0F` 和 `& 0x0F` 取高低 4 位——`byte` 是有符号的，`>>>`（无符号右移）才能正确处理负字节。
- 输出十六进制字母是**大写**，所以比对时 `signature.toUpperCase()`。
- `.getBytes()` 未指定字符集；因为三个参数都是 ASCII（token 字母数字、timestamp 数字、nonce 字母数字），默认字符集不影响结果。

#### 6.2 XML 工具 — [`XmlUtil`](../s-pay-mall-common/src/main/java/cn/bugstack/common/weixin/XmlUtil.java)

提供四条能力：

| 方法                             | 底层      | 用途                   |
| ------------------------------ | ------- | -------------------- |

```java
    writer.write("<![CDATA["); writer.write(text); writer.write("]]>");
```

#### 6.4 接入 Controller — [`WeixinPortalController`](../s-pay-mall-web/src/main/java/cn/bugstack/controller/WeixinPortalController.java)

**GET** **`receive`（验签）**

```java
@GetMapping(value = "receive", produces = "text/plain;charset=utf-8")
public String validate(@RequestParam(value="signature", required=false) String signature,
                       @RequestParam(value="timestamp", required=false) String timestamp,
                       @RequestParam(value="nonce",     required=false) String nonce,
                       @RequestParam(value="echostr",   required=false) String echostr) {
    try {
        if (StringUtils.isAnyBlank(signature, timestamp, nonce, echostr)) {
            throw new IllegalArgumentException("请求参数非法，请核实!");
        }
        boolean check = SignatureUtil.check(token, signature, timestamp, nonce);
        if (!check) return null;
        return echostr;          // 原样返回，微信才认为校验通过
    } catch (Exception e) {
        log.error("...", e);
        return null;
    }
}
```

三个设计选择值得注意：

| 写法                                      | 原因                                                |
| --------------------------------------- | ------------------------------------------------- |
| `required = false` + 手动校验               | 参数缺失时走自己的 catch 记日志，而不是 Spring 直接抛 400            |
| `produces = "text/plain;charset=utf-8"` | 必须原样返回 `echostr`；不指定 charset 会用 ISO-8859-1 导致中文乱码 |
| 失败 `return null`                        | 空响应体 → 微信判定校验失败，且不会触发重试风暴                         |

**POST** **`receive`（事件）**


## 7. 十个「为什么」技术点深挖

**Q1：为什么 GET 要验签？我们不是已经有 token 了吗？**
GET 验签解决的是「**微信怎么确认这个 URL 是我的**」，防止有人抢注回调地址。它是配置期的**一次性握手**，不是每次业务请求都跑。

**Q2：为什么签名要排序？**
微信只保证参数无序，排序是为了让双方对「拼接顺序」达成一致，否则同样的参数会算出不同签名。

**Q3：为什么 GET 返回** **`text/plain`** **而不是 JSON？**
微信只认「原样返回的 echostr」，任何包装（JSON/HTML）都会导致校验失败。

**Q4：为什么四个参数都写** **`required = false`？**
为了把「参数缺失」的异常处理权握在自己手里，统一记日志、安静返回 null，而不是让 Spring 抛 400。

**Q5：为什么 access\_token 要缓存 2 小时？**
微信 token 有效期 7200 秒且有调用频次限制；缓存过期时间与有效期对齐，既避免频繁调用，又不会用到过期 token。

**Q6：为什么 openid 映射放本地 Guava 而不是数据库？**
扫码登录是**短时一次性**场景，1 小时足够。放内存零 IO、天然带 TTL。代价是**多实例部署时不共享**（见第 8 节）。生产应换成 Redis。

**Q7：为什么用 Retrofit 而不是 RestTemplate/HttpClient？**
Retrofit 把「URL、方法、参数、请求体」全部前置到**接口注解**里，业务代码只剩一行方法调用，没有字符串拼接和手动序列化。代价是引入一层抽象的认知成本。

**Q8：为什么回包必须用 CDATA？**
消息内容可能包含 `<`、`&` 等 XML 特殊字符，不包 CDATA 会破坏报文结构，微信解析失败。

**Q9：为什么回包的** **`From/ToUserName`** **要互换？**
收包是「用户 → 公众号」，回包是「公众号 → 用户」，方向相反，字段自然对调。

**Q10：为什么用** **`Ticket`** **而不是** **`EventKey`** **关联会话？**
临时二维码的 `Ticket` 全局唯一且长度大、不可猜测；`EventKey` 在 `QR_SCENE` 模式下只是 `scene_id`（本例固定 100601，所有用户都一样），无法区分会话。

按风险等级排列，适合作为一次「代码审查练习」。

| # | 问题                         | 位置                             | 风险    | 说明                                                                  |
| - | -------------------------- | ------------------------------ | ----- | ------------------------------------------------------------------- |
| 1 | **POST 未验签**               | `WeixinPortalController.post`  | 🔴 高  | 接收了 `signature` 却从不校验，任何人可伪造 SCAN 事件直接调用 `saveLoginState`           |
| 2 | **无时间窗 / 无 nonce 去重**      | `SignatureUtil`                | 🔴 高  | 抓到一次合法请求即可无限重放                                                      |
| 3 | **密钥硬编码在 yml**             | `application-dev.yml`          | 🔴 高  | `app-secret` 进 Git 等于公众号可被接管                                        |

| 8 | **只处理 SCAN，未处理 subscribe** | `post` 的 if 判断                 | 🟡 低  | 新用户首次扫码走 `subscribe`，无法登录                                           |

```java
Boolean firstUse = redis.opsForValue().setIfAbsent(nonceKey, "1", 10, TimeUnit.MINUTES);
```

### 1. 「服务器配置 Token」和 `access_token` 的三点区别

| 对比维度 | 服务器配置 Token | access_token |
|---|---|---|
| **谁生成** | 你自己在公众号后台填写 | 微信 `cgi-bin/token` 接口返回 |
| **用途** | **验签**：证明回调请求来自微信 | **调用**：作为调用微信 API 的凭证 |
| **有效期** | 长期不变（除非你主动修改） | 7200 秒（2 小时），过期需重新获取 |

补充两点：

- 配置 Token 是**共享密钥**，安全性等价于它的保密性；`appsecret` 则更敏感，泄露可直接换取 access_token。
- 配置 Token 参与的是 `SHA-1(sort(token, timestamp, nonce))` 计算；`access_token` 只是拼在 URL 的 `?access_token=` 上，不参与签名。

对应代码：[SignatureUtil.check](../s-pay-mall-common/src/main/java/cn/bugstack/common/weixin/SignatureUtil.java#L10-L30)、[WeixinLoginServiceImpl#L44-L51](../s-pay-mall-service/src/main/java/cn/bugstack/service/impl/WeixinLoginServiceImpl.java#L44-L51)。

### 2. 手写验签四步

```
① 字典序排序：sort(token, timestamp, nonce)
② 按排序结果拼接成一个字符串
③ 对拼接串做 SHA-1，得到字节数组
④ 字节数组转十六进制（大写），与微信传来的 signature 比对
```

```java
public static boolean check(String token, String signature, String timestamp, String nonce) {
    String[] arr = new String[]{token, timestamp, nonce};
    sort(arr);                                          // ① 字典序
    StringBuilder content = new StringBuilder();
    for (String s : arr) content.append(s);             // ② 拼接
    MessageDigest md = MessageDigest.getInstance("SHA-1");
    byte[] digest = md.digest(content.toString().getBytes());  // ③ SHA-1
    String tmpStr = byteToStr(digest);                  // ④ 转十六进制大写
    return tmpStr != null && tmpStr.equals(signature.toUpperCase());
}
```

**为什么排序**：微信不保证参数顺序，排序让双方对拼接顺序达成一致，否则同样参数会算出不同签名。

**为什么用 `>>> 4 & 0x0F`**：`byte` 是有符号的，`>>>` 无符号右移才能正确处理负字节的高低 4 位。

### 3. 为什么 GET 必须返回 `echostr`，且必须是 `text/plain`

**必须返回 `echostr`**：微信的接入校验是「算对签名 + 原样复述挑战串」的双重验证。

| 动作 | 证明了什么 |
|---|---|
| 算对 `signature` | 你知道 Token（身份正确） |
| 原样返回 `echostr` | 你真的收到请求、响应体由你控制（通路正确） |

微信会把响应体与 `echostr` 做**字符串完全相等**比较，多一个字符都算失败。

**必须是 `text/plain`**：

- `text/plain` → Spring 用 `StringHttpMessageConverter` 把字符串**原封不动**写入响应体；
- 若声明成 `application/json`，Jackson 会把字符串序列化成 `"abc123"`（带引号），与 `echostr` 不等 → 校验失败；
- `charset=utf-8` 避免默认 ISO-8859-1 带来的编码问题。

对应代码：[WeixinPortalController#L33-L48](../s-pay-mall-web/src/main/java/cn/bugstack/controller/WeixinPortalController.java#L33-L48)。

### 4. `ticket` 在浏览器、微信服务器、后端之间如何流转

```
① 浏览器 → 后端：GET /api/v1/login/weixin_qrcode_ticket
② 后端 → 微信 API：POST cgi-bin/qrcode/create  →  拿到 ticket
③ 后端 → 浏览器：返回 ticket
④ 浏览器展示：https://mp.weixin.qq.com/cgi-bin/showqrcode?ticket=xxx
⑤ 用户扫码 → 微信服务器 → 后端：POST receive，事件 XML 里带 <Ticket>
⑥ 后端：openidToken.put(ticket, openid)      ← 用 ticket 作为关联键
⑦ 浏览器 → 后端：GET /api/v1/login/check_login?ticket=xxx
⑧ 后端：openidToken.getIfPresent(ticket) → 返回 openid
```

**核心**：`ticket` 是唯一贯穿「生成 → 展示 → 扫码 → 查询」四个阶段的关联键。前端全程只知道 ticket，openid 只存在于后端缓存与微信推送中。

### 5. `saveLoginState` 里为什么能拿到 `openid`

因为 **微信在回调 URL 上主动追加了 `openid` 查询参数**，Controller 用 `@RequestParam("openid")` 接住后传入。

```java
// 微信实际请求：
// POST /api/v1/weixin/portal/receive?signature=..&timestamp=..&nonce=..&openid=oXXXX
@RequestParam("openid") String openid

// 再传给业务层
loginService.saveLoginState(message.getTicket(), openid);
```

两个参数来自不同位置：

| 参数 | 来源 |
|---|---|
| `openid` | **URL 查询参数**（`@RequestParam`） |
| `ticket` | **XML 报文正文**（`XmlUtil.xmlToBean` 解析 `<Ticket>`） |

补充：`openid` 在 XML 的 `<FromUserName>` 里也有一份，代码选 query 参数是为了**不必先解析 XML 就能拿到用户标识**，便于尽早打日志。

### 6. 为什么 `openidToken` 是 1 小时、`weixinAccessToken` 是 2 小时

| 缓存 | 时长 | 依据 |
|---|---|---|
| `weixinAccessToken` | **2 小时** | 对齐微信 `expires_in = 7200` 秒，过期即失效，避免拿到过期 token |
| `openidToken` | **1 小时** | 业务选择的**短时登录窗口**，不是微信规定 |

`openidToken` 用 1 小时的原因：

1. 扫码登录是**短时一次性**行为，用户不会盯着二维码超过 1 小时；
2. TTL 越短，内存占用越小、泄露窗口越短；
3. 与二维码 30 天的 `expire_seconds` 解耦——**二维码可扫 30 天，但登录态只保留 1 小时**，两者本就该分开。

对应代码：[GuavaConfig#L15-L27](../s-pay-mall-web/src/main/java/cn/bugstack/config/GuavaConfig.java#L15-L27)。

### 7. 为什么 `Call` 叫「惰性请求」

因为 `retrofit.create()` 生成的代理在**调用接口方法时只构造请求描述，不发送网络请求**。

```java
Call<WeixinTokenRes> call = weixinApiService.getToken(...);  // 只构建，没发
WeixinTokenRes res = call.execute().body();                  // 这里才真正发送
```

内部过程：

```
调用 getToken(...)
  → 代理解析 @GET/@Query 注解
  → 构造 okhttp3.Request（URL、method、headers）
  → 包装成 Call 对象返回   ← 全程无 IO
  → execute() / enqueue() 才交给 OkHttp 执行
```

带来三个好处：

- 可以**延迟决定**发送时机；
- 同一个 `Call` 可以检查参数、加拦截、重试；
- 可自由选择同步 `execute()` 或异步 `enqueue()`。

### 8. 当前实现的 3 个安全问题及修复方式

| # | 问题 | 风险 | 修复 |
|---|---|---|---|
| 1 | **POST 未验签**：`signature` 接了但从没校验 | 任何人可伪造 SCAN 事件，直接写登录态 | 在 `post()` 入口调用 `SignatureUtil.check(...)`，失败直接返回 |
| 2 | **无时间窗、无 nonce 去重** | 抓到一次合法请求可无限重放 | 校验 `timestamp` 在 ±5 分钟内；用 Redis 的 `setIfAbsent` 对 nonce 去重并设 TTL |
| 3 | **密钥硬编码在 yml** | `appsecret` 进 Git，公众号可被接管 | 改用环境变量 / 配置中心 / KMS，并轮换已泄露的 secret |

```java
// 修复 1 + 2 的最小实现
boolean signOk = SignatureUtil.check(token, signature, timestamp, nonce);
boolean fresh = Math.abs(System.currentTimeMillis() / 1000 - Long.parseLong(timestamp)) <= 300;
boolean firstUse = Boolean.TRUE.equals(
        redis.opsForValue().setIfAbsent("weixin:nonce:" + nonce, "1", 10, TimeUnit.MINUTES));

if (!signOk || !fresh || !firstUse) {
    return "";
}
```

补充第 4 个（中高风险）：`XmlUtil.xmlToBean` 使用 `AnyTypePermission.ANY`，在 POST 未验签的前提下存在反序列化风险，应改为 `allowTypes(MessageTextEntity.class)`。

### 9. 画出两条独立的通信线

```
【出站线】我们主动调微信 —— 需要 access_token
后端 ──GET  /cgi-bin/token─────────────> api.weixin.qq.com
后端 ──POST /cgi-bin/qrcode/create─────> api.weixin.qq.com
后端 ──POST /cgi-bin/message/template──> api.weixin.qq.com

【入站线】微信主动推我们 —— 需要验签 + XML 解析
微信服务器 ──GET  receive?echostr=..──> 后端（一次性接入校验）
微信服务器 ──POST receive?openid=..────> 后端（扫码/消息事件，XML body）
```

三条理解要点：

- 两条线的**认证方式不同**：出站靠 `access_token`，入站靠 `signature` 验签；
- 两条线的**数据格式不同**：出站是 JSON，入站是 XML；
- 两条线的**发起方不同**：出站由业务触发，入站由用户行为触发。

### 10. 多实例部署必须改哪两处

| 必须改 | 原因 |
|---|---|
| **`openidToken` 缓存 → Redis** | 扫码请求可能打到实例 A，轮询打到实例 B；Guava 是进程内缓存，B 查不到 A 写入的映射 |
| **nonce 去重 → Redis（共享存储）** | 防重放需要全局唯一记录，本地 Map 在多实例下各记各的，等于没有防护 |

另外**隐含的第三处**：`weixinAccessToken` 缓存也应换成 Redis。虽然每个实例各自取 token 功能上能跑通，但会重复调用 `cgi-bin/token`，既浪费配额，也可能因微信 token 刷新机制导致互相失效。

对应改动位置：[GuavaConfig](../s-pay-mall-web/src/main/java/cn/bugstack/config/GuavaConfig.java)、[WeixinLoginServiceImpl 的 `@Resource Cache` 字段](../s-pay-mall-service/src/main/java/cn/bugstack/service/impl/WeixinLoginServiceImpl.java#L34-L39)。
